# Daily Tracker — v1 Design

Date: 2026-11-17
Status: Draft, awaiting approval

## Intent

Replace a paper sheet the owner fills in daily during a weight-loss period (2 Nov – 4 Dec): did I swim, did I avoid alcohol, when did I start/stop eating (fasting window), resting heart rate, weight — measured against a straight-line target weight (90 → 80 kg). The paper version works; the web app should make daily entry quick on a phone and show progress against the target without manual arithmetic.

v1 is for one person (the owner). It may later grow into a product with other users and an iPhone app, so the foundations should not need rebuilding for that — but v1 itself must stay very simple.

## Goals (v1)

- Log one entry per day from a phone browser in well under a minute.
- Fields per day (all optional, so partial days can be saved):
  - Swim (yes / no / not recorded)
  - No alcohol (yes / no / not recorded)
  - Blank means **not recorded**, never "no". It is only "no" when explicitly selected. Form control: tap-to-cycle (— → ✓ → ✗ → —). History shows the three states distinctly.
  - Start eating (time, HH:MM)
  - Stop eating (time, HH:MM)
  - Resting heart rate (integer bpm)
  - Weight (kg, one decimal)
- Eating window (stop − start, hours) is computed, not entered.
- Goals are a **list**, each with start date, start weight, end date, goal weight. Target weight for a day comes from the goal whose date range covers it, linearly interpolated (as on the sheet: 90.0 → 80.0 over 2 Nov – 4 Dec, ≈0.3 kg/day). The next planned goal is 80 → 77 kg; past goals are kept so the chart shows each period's target line. Days outside every goal have no target.
- Three screens:
  1. **Today** — entry form for a selected date (defaults to today; can pick a past date to fill gaps or correct). Shows target weight for that day.
  2. **History** — table resembling the paper sheet: date, swim, no-alcohol, start, stop, window, HR, weight, target. Tap a row to edit.
  3. **Chart** — actual weight vs target line over the goal period.
  Plus a small **Goals** screen: list goals, edit one, add a new one.
- Login required for everything. Only the owner can sign in.
- Push to `main` on GitHub deploys automatically.
- Running cost ≈ $0/month at this usage.

## Non-goals (v1)

- iPhone/native app (later; the API is designed so it can be a client).
- Multiple users / self sign-up, sharing with a coach or partner.
- Free-text notes / milestone annotations, reminders/notifications, exports, offline mode.
- Custom domain (CloudFront default URL is fine; can be added later).

## Anti-goals

- A sign-up page that lets strangers create accounts.
- Long-lived AWS access keys stored in GitHub.
- Data model that assumes a single user (would force a migration when it becomes an app).
- Infrastructure configured by hand in the AWS console (not reproducible).

## Approaches considered

| | Approach | Trade-off |
|---|---|---|
| A | Supabase (Postgres + Auth + RLS) + React on Cloudflare Pages | Least work, $0, Swift SDK for iPhone later. Free project pauses after 7 idle days. |
| **B (chosen)** | **AWS serverless: S3 + CloudFront, Cognito, API Gateway + Lambda, DynamoDB, all in IaC** | Near $0 and never pauses; full control and own API (also serves iPhone later). More moving parts and code to own. |
| C | Firebase (Auth + Firestore + Hosting) | Fast, free, good iOS SDK; document DB fits tabular/chart data less well, heavier lock-in. |

Owner picked **B**.

## Architecture

```
Phone browser
   │  HTTPS
   ▼
CloudFront ──► S3 (private bucket, React static build, OAC)
   │
   │  fetch with Cognito ID/access token (Bearer)
   ▼
API Gateway HTTP API ── JWT authorizer (Cognito user pool)
   │
   ▼
Lambda (Node.js 22, TypeScript) ──► DynamoDB table (on-demand)
```

### Frontend
- React + TypeScript, Vite build, mobile-first layout.
- Auth via AWS Amplify Auth library (`aws-amplify` v6, Auth category only) against Cognito — email + password login screen; no sign-up screen.
- Charting: Recharts.
- Config (user pool id, client id, API URL) injected at build time from CDK outputs.

### Auth & authorisation
- Cognito user pool, **self sign-up disabled**. The owner's user is created by an admin command (documented in README), not by the app.
- Hosted UI not used; app uses SRP login against the pool via Amplify.
- API Gateway JWT authorizer validates the token on every route.
- Lambda takes the user id **only from the token's `sub` claim**, never from the request. Every DynamoDB key is prefixed by that `sub`, so a user can only ever read/write their own data. This is the authorisation model now and when multi-user arrives.

### API (REST over HTTP API)
- `GET /entries?from=YYYY-MM-DD&to=YYYY-MM-DD` → list of day entries
- `PUT /entries/{date}` → create/replace that day's entry (idempotent)
- `DELETE /entries/{date}`
- `GET /goals` → list
- `PUT /goals/{startDate}` → create/replace a goal (goals must not overlap)
- `DELETE /goals/{startDate}`
- Input validated in Lambda (dates ISO, times HH:MM, HR 20–250, weight 20–400). One Lambda function with a small router is fine for v1.
- CORS limited to the CloudFront origin (plus localhost for dev).

### Data (DynamoDB, single table, on-demand billing)
| PK | SK | Attributes |
|---|---|---|
| `USER#<sub>` | `DAY#2026-11-16` | swim, noAlcohol, startEat, stopEat, restHr, weight, updatedAt |
| `USER#<sub>` | `GOAL#2026-11-02` | startDate, startWeight, endDate, goalWeight |

`swim` / `noAlcohol` are stored as `true`, `false`, or the attribute is absent (not recorded).

Range queries by date use `begins_with`/`between` on SK. Point-in-time recovery enabled (cheap, protects the only copy of the data).

Computed values (eating window, target weight) are derived in the frontend from stored fields, not stored.

### Infrastructure as code
- AWS CDK v2 in TypeScript (same language as app and Lambda), one stack per environment.
- v1 has a single environment (`prod`). Region: `ap-southeast-2` (Sydney).
- Stack contents: S3 bucket, CloudFront distribution (OAC, SPA fallback to `index.html`), Cognito user pool + app client, HTTP API + JWT authorizer, Lambda, DynamoDB table, and the GitHub OIDC deploy role (or that role in a small separate bootstrap stack).

### CI/CD (GitHub Actions)
- Monorepo: `/web` (React), `/api` (Lambda), `/infra` (CDK).
- **On pull request:** install, lint, typecheck, unit tests, `cdk synth` (and `cdk diff` if credentials available).
- **On push to `main`:** same checks, then `cdk deploy` (infra + Lambda), build web with stack outputs, `aws s3 sync` to the bucket, CloudFront invalidation.
- AWS access via **GitHub OIDC** → IAM role scoped to this repo's `main` branch. No stored AWS keys.

### Importing existing data (S3 event-driven import)
The paper sheet's days (2 Nov onward) are imported, not retyped through the UI.
- Private `imports` bucket (block public access, encrypted, writable only by the owner's admin role). Lifecycle rule deletes objects after 30 days.
- Upload `imports/<cognito-sub>/<name>.csv` → S3 `ObjectCreated` event → **Import Lambda**.
- Lambda parses CSV (columns: date, swim, noAlcohol, startEat, stopEat, restHr, weight; blank = not recorded), runs the **same validation module as the API**, writes valid rows with PUT semantics (idempotent: re-upload overwrites by date), and writes `<name>.csv.report.json` next to the file listing imported and rejected rows with reasons.
- The user id comes from the key prefix; only the admin can write to the bucket, so this is trusted.
- The initial CSV is transcribed by the builder from the photo of the paper sheet and checked by the owner before upload. Goal 90→80 (2 Nov – 4 Dec) is created through the Goals screen or API.
- Health data is never committed to git.

### Testing
- Import: CSV parsing, tri-state handling, rejected-row reporting.
- Lambda: unit tests for validation, routing and the "user id comes from token" rule (Vitest).
- Frontend: unit tests for target-weight interpolation and eating-window calculation (Vitest).
- CDK: a snapshot/assertion test that self sign-up is disabled and the API routes have the authorizer.

### Cost estimate
At one user: Cognito (free tier), Lambda/API Gateway (free tier / cents), DynamoDB on-demand (cents), S3 + CloudFront (free tier). Expected < $1/month. Set an AWS Budget alert at $5.

## Delivery order
The owner wants to use the app during the current period (ends 4 Dec), so build a thin end-to-end slice first:
0. **Slice 0 — pipeline first (changed 2026-11-17, owner's call):** monorepo skeleton, GitHub OIDC deploy role (bootstrap stack, deployed once by hand), app stack with S3+CloudFront serving a hello-world React page, GitHub Actions CI (PR) + deploy (push to `main`). The owner writes this code; the builder guides and reviews.
1. **Slice 1 — usable on phone:** Cognito, API, Lambda, DynamoDB added to the stack; entries + goals API, login + Today form. Shipped through the pipeline.
2. **Slice 2:** History screen, Chart, Goals screen.
3. **Slice 3:** S3 import + import of the paper data.
4. **Slice 4:** CDK tests, budget alert, pipeline hardening.
Each slice is deployable on its own. If time runs short, slices 3–4 can land after 4 Dec without blocking daily use.

## Setup is done by the owner
The owner runs all AWS and GitHub setup personally. The builder does not use AWS credentials; it delivers a step-by-step `docs/SETUP.md` runbook covering: AWS CLI profile, `cdk bootstrap`, first deploy, creating the Cognito user (`aws cognito-idp admin-create-user`), creating the GitHub repo, the OIDC role, repo variables, and uploading the import CSV. Values like region, the owner's email (Cognito user, budget alert) live in a gitignored config / CDK context, not hard-coded.

## Decided by the owner
- Single user now; may become a multi-user app later.
- Web app first, used mostly on phone; iPhone app later, out of scope.
- Straight-line target weight is the right model.
- Approach B (AWS serverless).
- Use it during the current period → thin slice first.
- Goals are a list; a future 80 → 77 kg goal is expected.
- Import paper data via a workplace-style mechanism (S3 event-driven import chosen).
- Swim / no-alcohol blank = not recorded; "no" only when explicitly selected.
- Owner does all AWS/GitHub setup personally.

## Calls made by the designer (open to correction)
- CDK in TypeScript over Terraform (one language across the repo).
- Region `ap-southeast-2`.
- Email + password via Cognito; no Sign in with Apple in v1.
- Project name `daily-tracker`.
- Single `prod` environment, no staging.
- Goals may not overlap.
- Imports bucket objects expire after 30 days.
- First slice deployed manually; CI/CD comes in slice 4.
- All fields are optional per day.
